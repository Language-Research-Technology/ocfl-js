# Concurrent writers are refused, not managed

## Context

A storage root is often an NFS mount shared between hosts, so more than one writer can reach an OCFL object at once: two processes on one host, or two hosts. Two writers that interleave can each publish a version built on files the other never saw, or leave a root inventory that doesn't match the versions on disk.

Each object has one lock, a file in the workspace (ADR 0002). A lock can outlive its writer: a process that is killed, or a host that loses power, never releases it.

After a host crashes, its caller may not know which objects it was writing. With a hashed layout an object's id can't be worked out from its directory, and a create that dies before its commit point leaves no inventory naming the id. One host's crash says nothing about writers on other hosts sharing the storage root.

Telling a dead writer from a slow one needs something the lock can't reliably give on shared storage. A process id means nothing on another host. A heartbeat or an expiry time depends on clocks that differ between hosts, and on a writer that can stall for minutes on a slow mount and then carry on. Operating-system file locks behave differently across NFS versions and servers, and can be lost silently. A wrong guess lets a second writer in while the first is still working, which is the damage the lock exists to prevent.

An opened OCFL object is the object as read at one moment. A writer can hold one that is no longer the head, because another writer has committed since.

Committing an update takes several filesystem steps: the new version directory is moved into the object root, then the root inventory is replaced, then its sidecar. Any of them can fail, and so can the clean-up after a failure. Putting the old root inventory back after a late failure lets a reader see the new head appear and then vanish, and a failure during that undo leaves the object in a state nobody chose. A caller who gets an error needs to know whether the version exists.

On NFS a rename can take effect while its reply is lost, so the call fails although the root inventory was replaced.

A create writes the object declaration before its root inventory, so for a moment, and for good if the writer dies there, the object root has a declaration and no inventory. A damaged object can look the same.

Two writers whose object roots nest hold different locks, so neither lock keeps them apart, and each one's checks for an enclosing object or a non-empty object root run before it takes its lock. One object's lock or unfinished version could also be at a path another object's writer uses. Only the path-direct layout can place one object root inside another: with an empty `suffix`, or with an id whose path has the suffix part-way through. The other built-in layouts place every object root at the same depth.

A storage root written by another tool can still hold an object inside another, at a directory the layout gives no object.

A dead writer can only have left certain things. It always leaves its lock, which it takes first and releases last. In the workspace it leaves the version it was assembling. In the object root it leaves, at most, staged root inventory files and one version directory the root inventory doesn't name: the version after the head, or for a create the first version, beside the declaration. A remove that dies leaves whatever of the object root it hadn't deleted yet.

## Decision

- **No layout nests object roots.** The path-direct layout refuses an empty `suffix`, and refuses with `ID_INCOMPATIBLE_WITH_LAYOUT` any id whose mapped path has a directory above the object root that ends with the suffix, such as `a/__object__/b`. It compares path segments ignoring case and Unicode normalisation form, as a case-insensitive file system names them, so `a/__OBJECT__/b` is refused too. So two objects' roots, and their directories in the workspace, are never one inside the other, and one object's lock decides who may write it. Opening, creating, removing and recovering still check for an object root inside another object, as another tool can leave one.
- **A second writer is refused straight away.** `root.create`, `object.update` and `root.remove` take the object's lock before anything else. If it is taken they throw `UPDATE_IN_PROGRESS` and change nothing. The library never waits or queues behind another writer.
- **Dead writers are not detected.** The library never expires a lock, and never removes one it didn't take. The lock records no process id, host or heartbeat, and no operating-system file lock is used.
- **The lock says whose it is and when it was taken.** It records the id of the object its writer is creating, updating or removing, and the time. `UPDATE_IN_PROGRESS` carries the time as `lockedAt`. Whether that is too long ago is for the caller to judge. Reading the time is best effort: a lock that exists is held even if it can't be read or isn't one this library wrote, and then `lockedAt` is absent.
- **A lock is written whole.** Its content is written to a file beside it and flushed to disk, then hard-linked to the lock, so a lock never exists half-written and of two writers linking at once only one succeeds. A change to a held lock is written beside it and renamed over it. On a file system without hard links the lock is created exclusively in place instead.
- **Recovering a write is checked against its writer.** `write.recover()` recovers only if the lock was taken by the writer that was listed: same id, time and object root. A writer that has since begun removing the object is still the same writer.
- **An out-of-date object is refused.** With the lock held, an update compares the head of the object it was called on with the head the root inventory on disk names, before the callback runs and again when it commits, before anything in the object root changes. If they differ it throws `OBJECT_OUT_OF_DATE` and discards the update. It does the same if the root inventory on disk isn't the one the object was opened from, which is how an object removed and created again under the same id is told apart. A create that finds a root inventory throws `OBJECT_EXISTS`.
- **A version is assembled in a directory its writer made.** With the lock held, the writer creates the version's directory in the workspace exclusively. If it is already there, left by a dead writer whose lock has gone, the update keeps its lock, changes nothing else and throws `RECOVERY_NEEDED`, so leftover files never become part of a version and the object becomes an unfinished write.
- **A create that isn't committed is not an object yet.** While an object root has a declaration, no root inventory and a held lock, `root.open` throws `OBJECT_NOT_FOUND` and `root.create` throws `UPDATE_IN_PROGRESS`. Without the lock that state is damage: `root.open` throws `INVALID_OBJECT` and `root.create` throws `OBJECT_EXISTS`. Opening a healthy object never looks at the lock.
- **An update has one commit point: the rename that replaces the root `inventory.json`.** Before it the update isn't committed, and after it the update is, whatever happens next. Nothing puts a replaced root inventory back.
- **A failure before the commit point discards the update.** Everything it made is removed, the lock is released, and the original error is thrown as it is. A retry starts from the object as it was.
- **A failure after the commit point throws `RECOVERY_NEEDED`**, with the failure as its `cause`, and keeps the lock. That covers replacing the sidecar and removing the lock. The version stays committed and nothing is undone.
- **A failed commit-point rename is checked against the disk.** If the root inventory then names the new head, or can't be read, the update is treated as past the commit point: `RECOVERY_NEEDED`, the lock kept, nothing undone. Only a root inventory that still names the old head lets the update be discarded.
- **A failure to discard an update throws `RECOVERY_NEEDED`** too, with the update's original failure as its `cause`, and keeps the lock.
- **The lock is released only when the update ends cleanly**: once it is committed and its sidecar is in place, or once it is discarded and everything it made is gone. An empty workspace directory that can't be removed is harmless, and doesn't count as a failure.
- **Locks are found as unfinished writes.** `root.unfinishedWrites()` lists one unfinished write for each lock in the workspace, with its `id`, `lockedAt` and whether it is `removing`; `root.unfinishedWrite(id)` finds the one for an id. A file named as a lock counts only if it holds a lock and sits where the layout places that lock's id. Listing changes nothing, and can't say which writers are dead.
- **An object is recovered only through its unfinished write.** There is no recovery by id alone, and none of every lock at once: after one host crashes, writers on other hosts may still be alive. `write.recover()` clears what its writer left, on the caller's word that the writer is dead. If another writer's lock has replaced the one listed it throws `UPDATE_IN_PROGRESS` and changes nothing; if the lock has gone it does nothing. Two recoveries of one write at once are not kept apart. It applies the commit-point rule to what it finds, and removes only what a dead writer can have left:
  - the unfinished version in the workspace, unless a lock is at or below it, and lock content staged and never put in place. No layout nests object roots, but a storage root an earlier release or another tool wrote can still hold another object's directory in the workspace below a version name, so recovery leaves alone any version directory holding another lock;
  - with a root inventory, the staged inventory files and the directory of the version after the head. A root inventory whose sidecar is stale or missing is a committed update, and is completed by writing the sidecar;
  - with no root inventory and a declaration, the create wasn't committed: the declaration, the first version and the staged inventory files are removed;
  - with a lock that says the object is being removed, the remove is finished: whatever is left of the object root is deleted, in whatever state it is;
  - with an object root that holds another id's object, or is inside another object, nothing in the object root: its writer was refused before writing there.

  Anything else is left alone. A declaration with no root inventory and a version other than the first is damage, not a dead create: recovery throws `INVALID_OBJECT` and changes nothing. The lock is released last. Recovery never makes a version the head.
- **A remove is committed when its lock says so.** `root.remove(id)` checks, with the lock held, that the id's directory holds that object. If it doesn't, it releases the lock and deletes nothing. If it does, it records in the lock that the object is being removed, and only then deletes the object root and the layout directories left empty above it. From that point the remove is carried through, by `root.remove` or by recovery: a failure throws `RECOVERY_NEEDED` and keeps the lock. In the workspace it deletes its own lock and what dead writers left there. The declaration, root inventory and sidecar are deleted last, so that a reader meanwhile finds the object rather than a damaged one.
- **A lock records whether the object root existed when it was taken.** That is how recovery tells an object root a dead create made, which it removes along with the layout directories left empty above it, from one that was already there, which it keeps.
- **A lock records that its object is being removed.** That is how recovery tells a partly deleted object, which it finishes deleting, from a damaged one, which it leaves alone.

## Consequences

- Retrying is the caller's choice. After `UPDATE_IN_PROGRESS` it can wait and try again; after `OBJECT_OUT_OF_DATE` it opens the object again and repeats the update.
- A slow writer is never trampled, however long it takes.
- A writer that dies leaves its lock, and the object can't be updated until someone who knows the writer is dead recovers its unfinished write. The library can't make that call; `lockedAt` is what it offers towards it.
- After a crash the caller finds every write the crashed host may have left by listing the unfinished writes, whatever the layout, and recovers the ones it judges dead. Recovering them all is a loop the caller writes, on its own judgement.
- Recovering a write whose writer is still alive destroys that writer's update, and lets a second writer in beside it. Nothing in the library guards against this, except that a write listed before its writer finished and another took the lock is refused.
- Recovery can be repeated: if it fails part-way the lock is still there, and recovering the write again finishes the job.
- On a file system without hard links, a crash while a lock is written can leave one this library doesn't recognise. It refuses writers but is no unfinished write, so it has to be removed by hand.
- `lockedAt` is the writer's own clock, so it is comparable across hosts only as far as their clocks agree.
- Only writers that use this library's lock are kept apart. Another tool writing to the same object is caught only if it has moved the head by the time the update checks it.
- Readers take no lock, so opening an object never waits on a writer.
- A path-direct storage root whose `config.json` sets an empty `suffix` can't be opened, even to read. An id that spells the suffix part-way through, such as `a/__object__/b`, can't be stored under path-direct at all. Ids that only start with another, such as `a` and `a/b`, are stored side by side.
- An object root inside another object, which another tool left, is reported rather than written: `INVALID_OBJECT` (E082) if it holds an object, `ID_INCOMPATIBLE_WITH_LAYOUT` if it doesn't. Recovering a write there releases its lock and touches nothing in the storage root.
- "Was the update committed?" has one answer, which the root inventory on disk gives. Any error other than `RECOVERY_NEEDED` means it wasn't, and the update can be repeated without applying a change twice.
- After `RECOVERY_NEEDED` the update may or may not be committed, and the caller must not simply repeat it. The object stays readable, and later updates of it throw `UPDATE_IN_PROGRESS` until it is recovered. The caller recovers it, opens it again, and repeats the update only if the head hasn't moved.
- After `RECOVERY_NEEDED` from a remove, the object is partly or wholly deleted, and recovering it deletes the rest. Until then it may still open, with files of its versions missing.
- Between the commit point and the sidecar's replacement, and for as long as a failure leaves it so, the root inventory doesn't match its sidecar. Opening an object allows for that: it accepts a root inventory that is identical to the head version's own inventory.
- An object that `RECOVERY_NEEDED` leaves locked holds one of a few things: a committed head whose sidecar is stale or missing, with the staged sidecar beside it; a complete object and only the lock; an uncommitted update's files, in the workspace or in the object root, that the root inventory doesn't name; or what a remove hadn't deleted yet.
- Every `RECOVERY_NEEDED` leaves the object locked, so the object is among the unfinished writes until it is recovered.
- A version left in the workspace with no lock, which only removing a lock by hand leaves, is no unfinished write. It blocks nothing until the next create, update or remove of the object, which turns it into one or deletes it.
- Recovery can't destroy a committed version: a damaged object that has lost its root inventory keeps every version directory, and a stray version directory that isn't the next one stays where it is.
- A dead create whose lock was removed by hand is no unfinished write, so it can't be recovered. Its object root has to be removed by hand too.
- A lock that two ids' writers share, because the layout maps both to one directory, is recovered through the write of the id it records.
- A lost rename reply costs a recovery, not a version: the caller gets `RECOVERY_NEEDED`, and the head on disk says the update was committed.
- The object `update` was called on is unchanged by a failed update, including one that was committed and then threw `RECOVERY_NEEDED`. Opening the object again shows what is on disk.
