# One filesystem-only package with no extension points

## Context

This library is meant to be the one place OCFL for JavaScript lives. Someone who needs another storage layout or digest algorithm should find it here, rather than having to discover and trust a separately published plugin.

Everything public becomes a commitment at 1.0. A registry, a hook, a backend interface or a class to subclass would have to stay compatible for plugins that may not exist, and would keep the set of supported layouts and algorithms out of sight of anyone reading this code.

The published types should change only on purpose, and every change to them should be visible in review rather than discovered by a consumer after a release.

## Decision

- **One package.** `@ocfl/ocfl-fs` is the only package, and it stores OCFL on a locally attached filesystem through `node:fs`.
- **No public backend API.** There's no store interface to implement and no filesystem to inject.
- **No extension or digest registration.** There are no registries, `register()` or `setup()` hooks, or hasher factories, and loading the library has no registration side effects.
- **Built-in layouts and digests only.** Both are fixed tables in the code. The layouts are official community extensions plus the library's own `000N-path-direct-storage-layout`, each chosen by name or `{ extensionName, ...params }`. A storage root declaring a layout the library doesn't implement is rejected with `UNSUPPORTED_LAYOUT`, even when a layout is configured.
- **Additions by pull request.** A new layout or digest algorithm is contributed to this repository.
- **Public classes are exported as types only.** `OcflObject`, `OcflStorage`, `OcflObjectTransaction`, `OcflObjectInventory` and `OcflObjectFile` can be named but not constructed or subclassed. Instances come from `storage()`, `createStorage()`, `loadStorage()` and the methods on what they return. Error classes stay values, so callers can use `instanceof`.
- **The API report is the contract.** `etc/ocfl-fs.api.md`, generated by api-extractor from the built declarations, lists the public API. It leaves out doc comments, so rewording one doesn't change it, but it marks members with no doc comment as `// (undocumented)`, so adding a symbol's first comment or removing its last one does. Symbols without a release tag are public. `pnpm lint:api` fails when the built API differs from the report, when api-extractor reports a warning (such as a public signature using a type the entry point doesn't export), or when it can't read the TypeScript output. It runs in CI.
- **When `lint:api` fails.** If the change to the API is intended, run `pnpm api:update` and commit the report diff with the change. If it isn't, fix the code and leave the report alone.
- **Members used only by their own class are `#private`.** A field, method or accessor that no other class uses, including a subclass, is a JavaScript private member named without a `_` prefix. The runtime enforces the privacy, and the member stays out of the published types and the API report.
- **Members shared between classes are `@internal`.** A member that another class or a subclass uses keeps its `_` prefix and is tagged `@internal`, and `stripInternal` removes it from the published types and the API report. Nothing hides it at runtime, and it gets no sharing mechanism of its own. A static factory that only the library calls is tagged the same way, and a constructor that only its own class calls is a TypeScript `private constructor`.
- **Every export states its type.** Exported functions, constants, and class methods, accessors and properties have explicit types where `isolatedDeclarations` can't infer them, and the build enforces it; the test configs leave it off. Literal initialisers and `as const` stay inferred. Where a type in the public API would be large, it gets a named type instead of an inline one. Public classes stay classes, and their method signatures are the contract, with no separate interfaces.

## Consequences

- A layout or algorithm isn't usable until it has been merged and released here. A storage root using an unimplemented layout can't be opened until someone contributes that layout.
- Storing OCFL anywhere other than a filesystem isn't supported, and tests use real temporary directories.
- A change that adds a registry, an injectable backend, a public base class or a value export of one of the public classes contradicts this decision, and needs a new ADR first.
- Every change to the public API shows up as a diff to the API report in its pull request. A diff that removes or changes something already in the report is a breaking change, committed as `feat!:` or with a `BREAKING CHANGE:` footer.
- `#private` members aren't inherited, so once a subclass or another class needs a member, it can no longer be `#private`. Tests can't reach `#private` members either, so they exercise them through the public API.
- `@internal` members can still be reached at runtime, and the source types still include them, so the library's own code and tests can use them. A consumer who reaches one gets no compatibility promise. A `private constructor` stays in the published types as `private constructor();`, so the compiler rejects `new` on the class there too.
- Editing a function body can't silently change a published signature: an export without an explicit type fails the build with an error pointing at it. TypeScript 7 has no command-line quick fix, so annotations are written by hand or with an editor's "add missing type annotation".
