# One filesystem-only package with no extension points

## Context

This library is meant to be the one place OCFL for JavaScript lives. Someone who needs another storage layout, or another algorithm for content, fixity or a layout's hashing of ids, should find it here, not in a separately published plugin they have to discover and trust.

Everything public is a commitment. A registry, a hook, a backend interface or a class to subclass would have to stay compatible for plugins that may not exist, and would hide the set of supported layouts and algorithms from anyone reading the code.

The published types should change only on purpose, and every change to them should be visible in review.

## Decision

- **One package.** `@ocfl/ocfl-fs` is the only package. It stores OCFL on a locally attached filesystem through `node:fs`.
- **No extension points.** There is no backend interface to implement, no filesystem to inject, and no registry or hook for storage layouts or algorithms. Loading the library registers nothing.
- **Storage layouts and algorithms are fixed tables in the code.** The layouts are official community extensions plus the library's own `000N-path-direct-storage-layout`. One is chosen with `{ extensionName, ...params }` when a storage root is created. A storage root is opened with the layout it declares, and one that declares a layout the library doesn't implement is refused with `UNSUPPORTED_LAYOUT`.
- **Additions come by pull request** to this repository.
- **The entry point exports an explicit list.** `src/index.ts` names every export: the functions `createStorageRoot()` and `openStorageRoot()`, the class `OcflError`, and types. It has no default export and no `export *`. Everything else is reached through those two functions.
- **The objects a storage root gives are published as interfaces.** `StorageRoot`, `OcflObject`, `Version`, `OcflFile`, `Draft` and `UnfinishedWrite` are interfaces, and the classes behind them aren't exported.
- **`OcflError` is the only published class, and only the library makes one.** It is a class so callers can use `instanceof`. It has no subclasses: callers test `code`. Its constructor is private, and the factory the library uses is tagged `@internal`, which `stripInternal` removes from the published types.
- **The API report is the contract.** `etc/ocfl-fs.api.md`, generated by api-extractor, lists the public API. `pnpm lint:api` runs in CI and fails when the built API differs from the report, when a public member has no doc comment, or when api-extractor warns, for example about a public signature that uses a type the entry point doesn't export.
- **Every export states its type.** The build sets `isolatedDeclarations`, so an export whose type can't be read off its declaration fails to compile.

## Consequences

- A layout or algorithm can't be used until it is merged and released here. A storage root that uses an unimplemented layout can't be opened.
- Storing OCFL anywhere but a filesystem isn't supported.
- Adding a registry, an injectable backend, a public base class, or a value export of a class behind one of the interfaces contradicts this decision and needs a new ADR first.
- Every change to the public API shows up in its pull request as a diff to the API report. A diff that removes or changes something already in the report is a breaking change.
- Editing a function body can't silently change a published signature.
