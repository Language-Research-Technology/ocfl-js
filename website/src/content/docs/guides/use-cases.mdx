This guide shows the library at work in common jobs, then lists the practices they share.

## A deposit service

A deposit service takes a directory of files, such as a finished upload, and stores it as an OCFL object. The first deposit for an id creates the object; each later one adds a version whose files are exactly the new deposit.

<Code code={depositService} lang="ts" />

- The service tries `root.create` first and catches [`OBJECT_EXISTS`](/ocfl-js/guides/errors/#object_exists), rather than checking whether the object exists. A check followed by a create can be beaten by another writer in between; the create can't.
- When the object exists, it opens it straight away and updates that. It never updates an object it opened earlier, which may no longer be the head.
- `draft.clear()` and then `draft.import(directory)` make the new version hold only the deposited files. Without `clear()`, files from the last version that aren't in the deposit would stay. See [Replacing](/ocfl-js/guides/updating-objects/#replacing) in Updating objects.
- Content already in the object is shared, not stored again. Depositing the same files twice writes no version: `update` returns the object it was called on, at the same version. See [An update that changes nothing](/ocfl-js/guides/updating-objects/#an-update-that-changes-nothing).
- `import` copies the whole directory or nothing. Its `filter` option can leave out files such as `.DS_Store`. It refuses a symbolic link the filter doesn't leave out with [`UNSUPPORTED_FILE_TYPE`](/ocfl-js/guides/errors/#unsupported_file_type), and throws [`SOURCE_CHANGED`](/ocfl-js/guides/errors/#source_changed) if a file changes while it is being copied, so deposit an upload only once it is complete.

Another writer can get in between the steps. If it purges the object after `create` throws `OBJECT_EXISTS`, `open` throws [`OBJECT_NOT_FOUND`](/ocfl-js/guides/errors/#object_not_found). If it commits a version after `open`, `update` throws [`OBJECT_OUT_OF_DATE`](/ocfl-js/guides/errors/#object_out_of_date). Neither commits anything, so `deposit` starts again from `create`, which makes the object again if it was purged. Running the build again is safe because it reads nothing from the object: whatever the head holds, the new version holds only the deposit. A build that decides what to change from files it read earlier mustn't be retried this way; see [Concurrent writers and recovery](/ocfl-js/guides/concurrent-writers/#object_out_of_date-the-object-changed-since-you-opened-it).

The retry limit keeps a busy object from looping forever. [`OBJECT_LOCKED`](/ocfl-js/guides/errors/#object_locked), when another writer holds the object's lock, isn't retried here: that writer may be slow or dead, and only you can judge which. See [Concurrent writers and recovery](/ocfl-js/guides/concurrent-writers/).

## A bulk load

A bulk load stores a whole catalogue at once, such as when a collection moves into OCFL. By default every create and update flushes each file it writes to disk before it returns, so that a deposit that returned is stored even if the power fails a moment later. Across many thousands of files that costs time, so a bulk load can turn it off for the storage root it opens, and flush everything once at the end.

<Code code={bulkLoad} lang="ts" />

- `durability: 'none'` holds for every create and update through that storage root, and every object opened or listed through it. Open the storage root again without it for writes that must be durable once they return.
- Until `sync` returns, a crash or power failure can leave an object written lately with empty or short files, and nothing reports it until a [fixity check](#checking-fixity-across-a-storage-root). Keep every source until then, so a damaged object can be removed and loaded again.
- The lock is flushed under either setting, so the rules in [Concurrent writers and recovery](/ocfl-js/guides/concurrent-writers/) hold the same. See [What survives a power failure](/ocfl-js/guides/concurrent-writers/#what-survives-a-power-failure).
- `createStorageRoot` takes the same option, for a bulk load into a new storage root.

## A read-only file server

A file server reads files from OCFL objects and sends them over HTTP. It never writes, so it takes no lock and never waits on a writer.

<Code code={fileServer} lang="ts" />

- The server opens the storage root once, and keeps each object it opens. An opened OCFL object is the object as read at one moment, so before using a kept one the server asks `object.isCurrent()`, and opens the object again once a version has been committed since. `isCurrent()` costs one `stat` of the root inventory, where opening reads and checks the whole inventory. It is a cheap check, not a guarantee; see [`OcflObject.isCurrent`](/ocfl-js/api/interfaces/ocflobject/#iscurrent).
- `file.stream({ start, end })` reads only the bytes asked for. [`start` and `end`](/ocfl-js/api/interfaces/streamoptions/) count bytes from 0, and `end` is included, as in an HTTP `Range` header. A range that starts after it ends, or after the file's last byte, rejects with `RangeError` before anything is read, which the server answers with `416`.
- A file's `digest` names its content, so it makes a good `ETag`: the same content has the same digest in every version.
- `file.modifiedAt` is when the version that gave the file its current content was committed, which makes a good `Last-Modified`. It comes from the inventory, not the stored file, so copying or restoring the storage root doesn't change it. Content changed back to an earlier content counts as a change, so the date is that of the change back, not the earlier version's.
- `await file.stream({ start, end })` opens and checks the stored file before it resolves. One that is missing or isn't a regular file rejects with `INVALID_OBJECT`, and one that can't be read rejects with the file system error, all before any headers are sent, so the server answers `500`. A stored file removed once the stream is open is still read in full.
- The stream holds the stored file open until it ends. `pipeline` destroys it if the client goes away; code that gets a stream and doesn't read it should `destroy()` it.
- To serve an earlier version, read its files from `object.version(number).files` instead of `object.head.files`. Convert the number from the request with `Number()` first, since a string throws a `TypeError`. A number that isn't a version, `NaN` among them, throws `VERSION_NOT_FOUND`, which the server can answer with a 404.

## A file's history

This lists each file of an object's head, with the version that added it and the version that gave it its current content:

<Code code={fileHistory} lang="ts" />

- [`createdIn`](/ocfl-js/glossary/#created-in) follows the logical path, not the content: a renamed file is created in the version of the rename, and one removed and later put back is created again in the version that puts it back.
- [`modifiedIn`](/ocfl-js/glossary/#modified-in) follows the content: content modified and later put back as it was is modified again in the version that puts it back.
- `createdAt` and `modifiedAt` come from the inventory, so restoring the storage root from a backup doesn't change them.
- A file read from an earlier version, through `object.version(number).file(path)`, gives its history up to that version.

## An indexing job

An indexing job lists every OCFL object in a storage root and records what it finds, for a search index or a catalogue.

<Code code={indexingJob} lang="ts" />

- `root.objects()` yields each object as it finds it, in no particular order. Reading it lazily keeps memory use flat however large the storage root is, and breaking out of the loop stops the walk.
- An object it can't open is yielded as `{ status: 'damaged', error, objectRoot, id? }`, where `error` is an [`OcflError`](/ocfl-js/api/classes/ocflerror/) with code [`INVALID_OBJECT`](/ocfl-js/guides/errors/#invalid_object), and the listing carries on. The job keeps these errors and reports them at the end, so one damaged object root doesn't stop the index or go unnoticed. Their `ocflCode`, when present, names the OCFL rule the object breaks.
- A file system error, such as a directory it can't read, is thrown, not yielded, and ends the listing.
- The listing leaves out an object that has lost its declaration and [a create whose writer died](/ocfl-js/guides/concurrent-writers/#a-create-whose-writer-died), without an error. See [what the library doesn't check or do](/ocfl-js/#what-it-doesnt-check-or-do).

## Checking fixity across a storage root

This job runs a fixity check on every object in a storage root and reports what has changed or gone missing since it was stored.

<Code code={fixityCheck} lang="ts" />

`checkFixity()` reads every stored file listed in the object's manifest again and compares its digest with the one the inventory records. It returns a [`FixityReport`](/ocfl-js/api/interfaces/fixityreport/): `problems` holds one [`FixityProblem`](/ocfl-js/api/interfaces/fixityproblem/) for each stored file that fails, so an empty list means every stored file matches, and `checkedFiles` says how many stored files it read.

Each problem's `kind` says what it found:

- **a missing file:** the manifest lists a stored file, and there is no regular file at its path (`missing`);
- **changed content:** a stored file whose digest no longer matches the one recorded for it (`changed`).

More kinds may be added, so handle each by name.

It doesn't find:

- **a logical path pointing at the wrong content.** The check compares each stored file with its own digest. It doesn't check that each file in a version is the content you meant it to be. If a writer recorded `notes.txt` against another file's digest, every stored file still matches and the check reports nothing.
- **extra files** that the inventory doesn't list;
- **problems in the `fixity` block** of the inventory, which it doesn't read.

It isn't validation: an object can pass the fixity check and still break the OCFL specification. To check that, use an OCFL validator, as described under [Objects written by other tools](/ocfl-js/#objects-written-by-other-tools).

A stored file that is there but can't be read, such as `EACCES` or `EIO`, throws instead of being reported. The job catches that for each object, so one unreadable file doesn't end the run.

`checkFixity({ signal, onProgress })` can be cancelled and report how far it has got:

- `onProgress` is called after each stored file is checked, whether it passed, changed or is missing, with `checkedFiles` and `totalFiles`. `checkedFiles` reaches `totalFiles` before the check resolves. If `onProgress` throws, the check stops and rejects with that error.
- Aborting `signal` stops the check, which rejects with the signal's `reason`. No stored file is still open or being read once it has rejected. The job above gives the whole run six hours, and stops at the object it was checking when time runs out.

Each problem names the stored file by its path from the storage root, as `storedFile`, and lists in `affects` every version and logical path that reads it, so you can see which of your files are hit. It is empty for a stored file no logical path reads, such as a second copy of one digest's content. Repair it by hand: copy a good copy from a backup to `storedFile` under the storage root. Writing the content again with `object.update` doesn't repair it, because an update that finds the content's digest already in the object keeps the stored file it has.

Both digests are lowercase, even when an object written by another tool records them in uppercase.

## Writing a version out

This job writes version 1 of an object to a directory, each file under its logical path, with [`version.exportTo`](/ocfl-js/api/interfaces/version/#exportto):

<Code code={writeVersionOut} lang="ts" />

- The directory must be missing or empty, and outside the storage root. `exportTo` makes a missing one, with its parents, and refuses one with anything in it with [`DIRECTORY_NOT_EMPTY`](/ocfl-js/guides/errors/#directory_not_empty) before it writes anything. It writes the version's files and nothing else.
- Each file's modification time is its [`modifiedAt`](/ocfl-js/api/interfaces/ocflfile/#modifiedat): the time of the version in which it took its content, from the inventory.
- Every file lands inside the directory. Opening an object refuses one with a logical path that leaves it, such as `../../etc/passwd`, so you don't need to check the paths yourself. `exportTo` never writes over a file, but it makes directories by path, so export to a directory nobody else can write to while the export runs: someone who can could swap a directory for a link to somewhere else.
- `onProgress` is called after each file is written. Aborting `signal` stops the export, which rejects with the signal's `reason`, and no stored file is still open once it has rejected.
- An export that fails or is aborted leaves what it had written, including a file only partly written. Empty the directory before you export to it again.
- Nothing is flushed to disk. Run the system `sync` command if you need the files to survive a crash.

## Best practices

- **Open the object fresh before updating it.** An opened OCFL object doesn't change when another writer commits a version. Updating one that is no longer the head throws [`OBJECT_OUT_OF_DATE`](/ocfl-js/guides/errors/#object_out_of_date), so open it just before the update, and open it again before you retry. Within one process, use the object each update returns for the next: see [How an update works](/ocfl-js/guides/updating-objects/#how-an-update-works). [Concurrent writers and recovery](/ocfl-js/guides/concurrent-writers/#object_out_of_date-the-object-changed-since-you-opened-it) shows the retry.
- **Catch [`OBJECT_NOT_FOUND`](/ocfl-js/guides/errors/#object_not_found) instead of checking whether the object exists first.** Call `root.open(id)` and catch the error, or call `root.create` and catch [`OBJECT_EXISTS`](/ocfl-js/guides/errors/#object_exists). A separate check can be out of date by the time you act on it. `root.has(id)` answers cheaply, without reading the inventory, when you only need to know, such as to show it; don't follow it with a `create` that relies on it.
- **Handle damaged object roots while listing.** `root.objects()` yields `{ status: 'opened', object }` for each object and `{ status: 'damaged', error, objectRoot, id? }` for each object root it can't open. Switch on `entry.status` with a case for each, and keep a `default` that skips anything else: a later release may add a status. Record `objectRoot` so each damaged object root gets looked at.
- **Run fixity checks regularly.** Disks fail, and files get changed by hand, without anyone noticing until the content is read. A regular check finds this while you still have a good copy to restore from. A check reads every stored file, so its time grows with the size of the storage root: run it when the storage is quiet, or spread the objects over several runs, and keep each run's report. [Scheduling fixity checks](/ocfl-js/guides/looking-after-a-storage-root/#scheduling-fixity-checks) shows how.

See [`StorageRoot`](/ocfl-js/api/interfaces/storageroot/), [`OcflObject`](/ocfl-js/api/interfaces/ocflobject/) and [`OcflFile`](/ocfl-js/api/interfaces/ocflfile/) in the API reference for every error each method throws, and [Errors](/ocfl-js/guides/errors/) for what to do about each.
