The library throws one error class, [`OcflError`](/ocfl-js/api/classes/ocflerror/), for anything you might handle. This page lists every value of its `code`, what causes it, and what to do. Coming from 0.4, which threw plain `Error`s? See [Upgrading from 0.x](/ocfl-js/guides/upgrading-from-0-x/).

## Catching an `OcflError`

Recognise one with `isOcflError(error)`, then test `code`. `isOcflError(error, 'OBJECT_LOCKED')` tests both, and tells TypeScript the code. Unlike `instanceof OcflError`, it also recognises an error from another installed copy of this release or a later one. The message names the object by its id, as `<id>`, and gives a path only where a person may need to look on disk. It is useful in logs, but it isn't part of the contract and may change. New codes can arrive in a minor release, so a `switch` on `code` keeps a `default` branch.

:::caution
Messages can contain absolute paths on the server, including the paths of stored files. No field gives a path in the storage root. Log them, but don't send `error.message` back in an HTTP response or show it to the people using your service.
:::

These fields are set only some of the time. Read them, rather than parsing the message:

- `objectId` is the id of the object the error is about. Every code about one object sets it. Codes about the storage root as a whole don't, and nor does `INVALID_OBJECT` when the fault leaves the id unknown, such as an inventory its sidecar doesn't confirm.
- `logicalPath` is the logical path at fault, as the inventory lists it, for [`FILE_NOT_FOUND`](#file_not_found), [`PATH_CONFLICT`](#path_conflict), [`TARGET_NOT_EMPTY`](#target_not_empty) and [`INVALID_LOGICAL_PATH`](#invalid_logical_path).
- `sourcePath` is the file `import` couldn't take, for [`SOURCE_CHANGED`](#source_changed) and [`UNSUPPORTED_FILE_TYPE`](#unsupported_file_type): the `source` you gave `import`, joined, as `path.join` does, with the file's path below it, and not resolved.
- `ocflCode` is the code the OCFL specification gives the rule that was broken, such as `E060`, when the fault has one. Only `INVALID_OBJECT` and `INVALID_STORAGE_ROOT` carry one.
- `lockedAt` is when another writer took the object's lock. Only `OBJECT_LOCKED` sets it, and it is absent if the lock couldn't be read or was released in the meantime.

`cause`, when set, is the error underneath. `RECOVERY_NEEDED` always sets it, and so does a code the library throws because a file system call failed in a way it knows the meaning of, such as `CROSS_FILESYSTEM_MOVE`. Finding nothing at a path, or finding a lock taken, isn't such a failure: `OBJECT_NOT_FOUND` and `OBJECT_LOCKED` don't carry the file system error.

### What isn't an `OcflError`

- A `TypeError` means the call itself was wrong: a required argument is missing or empty, an argument has the wrong type, an options object has an extra key, a version's `createdAt` is earlier than the head version's, or `createStorageRoot` was given a storage layout or parameter it doesn't have or refuses. The API reference lists each method's.
- A `RangeError` means a byte range given to `OcflFile.stream()` has an end that isn't a whole number from 0, a `start` after its `end`, or a `start` after the file's last byte.
- A plain `Error` means a draft was used after its update finished, or an update ended with draft operations still running. Await every operation.
- An aborted `signal` rejects `checkFixity`, `create`, `update`, `objects()`, or an `OcflFile`'s `stream()`, `text()` or `bytes()` with the signal's `reason`, whatever that is: an `AbortSignal.timeout()` gives a `TimeoutError` `DOMException`, and `controller.abort()` with no reason an `AbortError` one. A stream that `stream()` has already handed out is the exception: it is destroyed with Node's `AbortError`, whose `cause` is the reason.
- File system errors, such as `ENOSPC` or `EACCES`, pass through untouched, with two exceptions. Where the library knows what one means, it throws the code for that meaning, such as [`CROSS_FILESYSTEM_MOVE`](#cross_filesystem_move), [`UNSUPPORTED_FILESYSTEM`](#unsupported_filesystem) or, for a stored file that is missing, [`INVALID_OBJECT`](#invalid_object). Where one leaves a write needing recovery, it throws [`RECOVERY_NEEDED`](#recovery_needed).

None of these is retryable as it stands. Fix the call, or the file system. An abort is the caller's own choice, so whether to try again is too.

## Storage roots

### `DIRECTORY_NOT_EMPTY`

**Cause:** `createStorageRoot` or `version.exportTo` was given a directory that already has something in it.

**What to do:** create the storage root, or export the version, in an empty or missing directory. To use a storage root that already exists, call `openStorageRoot`.

`createStorageRoot` writes the `0=ocfl_1.1` declaration last, so one that was interrupted, by a crash or a killed process, leaves a directory with no declaration, or an empty one. `openStorageRoot` refuses it with `INVALID_STORAGE_ROOT`, and `createStorageRoot` with this code. Delete what is in the directory and call `createStorageRoot` again, but only if the directory holds nothing but some of these, any of which may be empty or cut short:

- `ocfl_1.1.md`
- `ocfl-js-workspace.md`
- `ocfl_layout.json`
- `000N-path-direct-storage-layout.md`, if the storage layout is `000N-path-direct-storage-layout`
- `extensions/<storage layout>/config.json`, or the directories on its path
- an empty `0=ocfl_1.1`

`version.exportTo` gives this code before it writes anything. An export that failed or was aborted leaves what it had written, so empty the directory before you export to it again.

### `STORAGE_ROOT_NOT_FOUND`

**Cause:** `openStorageRoot` was given a path that doesn't exist, or an empty directory. There is no storage root there.

**What to do:** to make one, call `createStorageRoot` with the same path. To open a storage root, or create it if it isn't there, catch this code and nothing else:

### `INVALID_STORAGE_ROOT`

**Cause:** `openStorageRoot` found no storage root it can read: the path is a file, is below a file, or is a directory with something in it, and its `0=ocfl_1.x` declaration is missing or wrong (`ocflCode` `E069` or `E080`), its `ocfl_layout.json` doesn't name a storage layout (`E070`), or the storage layout's `config.json` isn't a JSON object, is for another storage layout, or has a parameter the storage layout doesn't have or a value it refuses.

**What to do:** check the path is a storage root. If it is, fix the declaration, `ocfl_layout.json` or `config.json`; the message names the file. A directory with no declaration, or an empty one, may be what an interrupted `createStorageRoot` left: see [`DIRECTORY_NOT_EMPTY`](#directory_not_empty).

### `LAYOUT_NOT_DECLARED`

**Cause:** `openStorageRoot` found a storage root with no `ocfl_layout.json`. OCFL allows that, but without it the library can't tell where each object is, and it doesn't guess.

**What to do:** add an `ocfl_layout.json` naming the storage layout the root's objects are laid out by, such as `{"extension": "0004-hashed-n-tuple-storage-layout"}`, with that storage layout's `config.json` under `extensions/` if it doesn't use the default parameters. The message lists the storage layouts the library has.

### `UNSUPPORTED_LAYOUT`

**Cause:** `openStorageRoot` found a storage root whose `ocfl_layout.json` names a storage layout the library doesn't have. The library has four: `0002-flat-direct-storage-layout`, `0003-hash-and-id-n-tuple-storage-layout`, `0004-hashed-n-tuple-storage-layout` and the local `000N-path-direct-storage-layout`.

**What to do:** the message names the storage layout the root declares and lists the ones the library has. To open the storage root with this library, [ask for the storage layout to be added](https://github.com/Language-Research-Technology/ocfl-js/issues); until then, use another tool for it. A caller can't plug in a storage layout of its own.

## Finding objects

### `OBJECT_NOT_FOUND`

**Cause:** there is no object with this id: nothing is in the directory the storage layout maps it to, or the storage layout can't place an object with this id at all, so none can exist (`cause` is then the storage layout's [`ID_INCOMPATIBLE_WITH_LAYOUT`](#id_incompatible_with_layout)). `open` also throws it for an object another writer is creating and hasn't committed.

**What to do:** catch it instead of checking whether the object exists first; a check can be out of date by the time you act on it. To make the object, call `create`, unless `cause` is `ID_INCOMPATIBLE_WITH_LAYOUT`: then no object can have the id, and `create` refuses it too.

### `OBJECT_EXISTS`

**Cause:** `create` found an object already there, or another writer created it first.

**What to do:** open the existing object, and `update` it if you meant to change it.

### `ID_INCOMPATIBLE_WITH_LAYOUT`

**Cause:** a writer was given an id the storage root's storage layout can't place an object with. Either the storage layout can't map the id, or it maps it somewhere an object can't go: the storage root itself, outside it, the `extensions` directory, or a path too long for the file system (with the path-direct storage layout, an id of many long segments). Each storage layout has its own rules. For example, `0002-flat-direct-storage-layout` refuses an id with a `/` in it, `.`, `..`, `extensions`, or an id longer than 255 bytes, and the path-direct storage layout refuses an id with `.` or `..` segments, or one that ends with or contains its suffix.

`create` and `purge` also throw it when the object's lock in the workspace would be too long for the file system, even if its directory isn't, so such an object can be opened but not changed.

The id is at fault, not what is in the storage root. Only `create`, and `purge` for a lock path that is too long, throw it. Otherwise no object can have such an id, so `has` gives `false`, `unfinishedWrite` gives `undefined`, and `open` and `purge` throw [`OBJECT_NOT_FOUND`](#object_not_found).

**What to do:** choose another id, or a storage layout that suits your ids.

### `OBJECT_ROOT_CONFLICT`

**Cause:** the storage layout places the id, but the directory it maps to holds the wrong thing. `open` and `purge` throw it when that directory holds an object with a different id, or has no object declaration but holds other files, is a file, or is below one. `create` throws it when the directory isn't empty, is a file or is below one, or is inside another object, and also, rarely, when something appeared in the directory while the object's first version was being built. `unfinishedWrite` throws it when the object's lock in the workspace belongs to a writer of a different id.

The storage root is in a state a person needs to look at, often from an object moved or copied by hand, or written by a tool with another storage layout. A server should log it, not treat it as not found.

**What to do:** don't retry. Look at what is in the directory before doing anything; the message names it.

### `INVALID_OBJECT`

**Cause:** what the library read where the object should be isn't an object it can safely use. The inventory is missing, isn't JSON, is inconsistent, or names paths that would lead outside the object; the sidecar digest is missing or doesn't match; the object declaration is missing or wrong, or declares a later OCFL version than the storage root's; or the object is inside another object. Reading a file throws it if its stored file is missing or isn't a regular file, such as a directory, with the file system error, if any, as its `cause`. `ocflCode` names the OCFL rule, for example `E003` (no object declaration), `E033` (inventory isn't JSON), `E060` (sidecar digest doesn't match) or `E081` (a 1.1 object in a 1.0 storage root).

`open`, `update`, `purge`, recovering an unfinished write, `objects()`, and an `OcflFile`'s `size()`, `stream()`, `text()` and `bytes()` can all give it. `update` throws it if the declaration has been damaged since the object was opened, or removed while anything remains in the object root. Rarely, `create` throws it when an invalid declaration appeared in the new object root while its first version was being built.

These are checks the library makes before it uses an inventory's values as file paths. They are not validation: an object that opens can still break OCFL rules the library never looks at. To check an object against the specification, use [an OCFL validator](/ocfl-js/#objects-written-by-other-tools). See [It doesn't validate](/ocfl-js/#it-doesnt-validate) for what the library checks and what it doesn't.

**What to do:** don't retry; the object is damaged and needs a person to look at it. Repair it with the tool that made it, or from a backup. If you no longer want it, `purge` it, or, if `purge` refuses because the object can't be opened, see [Removing a damaged object root](#removing-a-damaged-object-root).

### `MUTABLE_HEAD_ACTIVE`

**Cause:** `update` found an active mutable head (`extensions/0005-mutable-head`) in the object. The library doesn't support that extension.

**What to do:** commit or discard the mutable head with the tool that made it, then update the object.

### `VERSION_LIMIT_REACHED`

**Cause:** `update` can't name the next version. The object's version names are zero-padded, and OCFL requires a padded name to start with a zero, so `v01` to `v09` allows nine versions and `v001` to `v099` allows 99. Objects this library creates aren't padded and never reach a limit.

**What to do:** the library can't add a version to this object. See [When the object is full](#when-the-object-is-full).

## Writers and locks

### `OBJECT_LOCKED`

**Cause:** `create`, `update`, `purge` or recovering an unfinished write found the object's lock taken: another writer is creating, updating or purging it, or died doing so. The library refuses straight away, never waits, and never removes a lock because of its age. `lockedAt` says when the lock was taken.

**What to do:** wait and try again. If you know the writer is dead, recover the object's unfinished write, from `root.unfinishedWrite(id)`, and then try again. Only recover it when its writer is no longer alive: recovering destroys a live writer's update. Recovering a write also throws `OBJECT_LOCKED`, changing nothing, if another writer took the lock after you got the write. See [`OBJECT_LOCKED` in Concurrent writers and recovery](/ocfl-js/guides/concurrent-writers/#object_locked-another-writer-holds-the-lock), and [A lock the library can't read](/ocfl-js/guides/concurrent-writers/#a-lock-the-library-cant-read) if `lockedAt` stays absent and `root.unfinishedWrite(id)` keeps giving `undefined`.

### `OBJECT_OUT_OF_DATE`

**Cause:** `update` found that a later version was committed after you opened the object, or the object was purged, whether or not it was created again. It is checked before your change runs and again just before commit. Nothing is committed.

**What to do:** open the object again and repeat the update against the new head. If the object was purged, opening it throws `OBJECT_NOT_FOUND`. See [`OBJECT_OUT_OF_DATE` in Concurrent writers and recovery](/ocfl-js/guides/concurrent-writers/#object_out_of_date-the-object-changed-since-you-opened-it) for a retry loop.

### `RECOVERY_NEEDED`

**Cause:** a write failed at a point where the library can't tell, or can't put right, what happened. That is one of:

- `create` or `update` failed after the commit point, or failed replacing the root inventory in a way that may have replaced it. The update may have been committed.
- A failed update couldn't remove everything it had made.
- `purge` failed part of the way through, so the object may be partly deleted.
- `purge` deleted the object but couldn't release its lock.
- `create`, `update` or `purge` was refused and couldn't release the lock it had taken. Apart from the lock, nothing is changed.
- An earlier writer left an unfinished version in the workspace. This is thrown before your change runs.

`cause` is the underlying failure. The object stays locked, so later writes get `OBJECT_LOCKED` until it is recovered, and it is among the storage root's unfinished writes. It can still be read.

**What to do:** don't simply repeat the write. Once no writer of the object is alive, recover its unfinished write: `(await root.unfinishedWrite(id))?.recover()`. After a `create` or `update`, open the object again and look at the head to see whether your version was committed; retry only if it wasn't. After a `purge` that had begun deleting, recovering finishes purging the object. After a refused write, recovering only releases the lock: nothing was changed, so repeat the write. See [`RECOVERY_NEEDED` in Concurrent writers and recovery](/ocfl-js/guides/concurrent-writers/#recovery_needed-the-update-may-or-may-not-be-committed).

### `CROSS_FILESYSTEM_MOVE`

**Cause:** the new version couldn't be moved from the workspace (`extensions/ocfl-js-workspace` in the storage root) into the object, because the two are on different file systems. `cause` is the `EXDEV` error. Nothing is committed.

**What to do:** keep the whole storage root on one file system. A mount point inside the storage root splits it.

### `UNSUPPORTED_FILESYSTEM`

**Cause:** `create`, `update` or `purge` couldn't take the object's lock, because the storage root's file system refused to hard-link it. Usually the file system has no hard links, as FAT, exFAT, most FUSE object-store mounts and SMB shares without POSIX extensions don't. `cause` is the underlying error; an `EPERM` can also come from an immutable or append-only directory. Nothing is changed and no lock is left.

**What to do:** move the storage root to a file system with hard links, such as a local Linux file system or NFS. Reading works where it is. If the file system has hard links, check the attributes of the workspace (`extensions/ocfl-js-workspace`) with `lsattr`.

## Drafts

These come from draft operations inside the function you pass to `create` or `update`. Unless you catch them there, the whole update is discarded, the object is left as it was, and the error is thrown from `create` or `update`. [Updating objects](/ocfl-js/guides/updating-objects/) describes each operation.

### `FILE_NOT_FOUND`

**Cause:** one of these found nothing at the path:

- `version.file()`: no file in that version. A directory isn't a file.
- `copy`, `rename` or `remove`: no file or directory in the draft.
- `reinstate`: nothing in that version.

**What to do:** check the path against the version's `files`, or against `object.head.files` for a draft operation. `logicalPath` is the path that wasn't found: the source, for `copy` and `rename`. Where a missing file is a normal outcome, such as a request for a path that may not exist, use `version.files.get(path)`, which gives `undefined` instead of throwing. It looks the path up exactly as written, without normalising it, so `./a.txt` or `a.txt/` isn't found there.

### `VERSION_NOT_FOUND`

**Cause:** the version number isn't there:

- `object.version()`: the object has no version with that number.
- `reinstate`: the object hasn't committed it. That includes one past the head, the version the draft is making, and one that isn't a whole number from 1.

**What to do:** take the number from `object.versions`, or use `object.versions.get(number)`, which gives `undefined` instead of throwing.

### `PATH_CONFLICT`

**Cause:** the operation would make a logical path both a file and a directory: a file where a directory is, or a file below another file. Writing over a file is allowed, and doesn't throw this.

**What to do:** remove what is in the way first. `logicalPath` is the path that would conflict, which for a directory copied or renamed may be a file below its target.

### `TARGET_NOT_EMPTY`

**Cause:** `copy` or `rename` was given a directory and a target that already has files, without `{ merge: true }`.

**What to do:** pass `{ merge: true }` to put the directory's files in among the target's, replacing files at the same paths. To replace the target instead, remove it first. See [Merging directories](/ocfl-js/guides/updating-objects/#merging-directories).

### `INVALID_LOGICAL_PATH`

**Cause:** a logical path is empty, absolute, or has a `..` segment (a backslash counts as a separator); a `copy` or `rename` target is inside its source; or an `import` target is empty or names the top of the object, such as `.`.

**What to do:** use a relative path without `..`. `logicalPath` is the path refused, exactly as you gave it if it is absolute or has `..`, and absent if it is empty. To import a directory's contents at the top of the object, leave out the target.

### `SOURCE_CHANGED`

**Cause:** a file changed while `import` was copying it in: the copy's digest doesn't match the source.

**What to do:** retry once nothing is writing to the source. `sourcePath` is the file that changed.

### `UNSUPPORTED_FILE_TYPE`

**Cause:** `import` found a symbolic link, socket, device or anything else that isn't a regular file or directory. `sourcePath` is what it found.

**What to do:** import the files the link points to, or, for a link below the source, leave it out with `import`'s [`filter` option](/ocfl-js/guides/updating-objects/#leaving-files-out).

## When the library offers no way forward

### When the object is full

An object with zero-padded version names that has reached `VERSION_LIMIT_REACHED` can't take another version from this library. Either:

- update it with the tool that made it, if that tool can renumber or otherwise carry on; or
- copy its head into a new object, which has no padding and no limit. The new object needs a new id while the old one exists, and it starts again at version 1, so the earlier versions stay only in the old object.

### Removing a damaged object root

`purge` refuses an object it can't read with `INVALID_OBJECT`, because it can't confirm the directory holds the object you named. Nothing is deleted.

If you are sure you want it gone:

1. Make sure no writer of the object is alive.
2. Delete the damaged object root by hand: the directory `objects()` gives as `objectRoot`, inside the storage root. It is where the storage layout places the id.
3. If the workspace (`extensions/ocfl-js-workspace` in the storage root) has a directory at the same path, delete that too.
4. Remove any parent directories that leaves empty, up to the storage root.
