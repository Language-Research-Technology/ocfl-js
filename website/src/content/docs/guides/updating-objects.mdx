Every change to an OCFL object is one update, and every update adds at most one version. This guide covers what you can do in an update, the order things happen in, and what an update records.

## How an update works

`object.update(options, change)` gives your `change` function a [draft](/ocfl-js/api/interfaces/draft/): the changes being assembled for the next version. The draft starts with the files of the head version. Your function changes it, and when the function returns, the draft is committed as one new version.

<Code code={draftOperations} lang="ts" />

- **All or nothing.** If `change` throws, or a draft operation throws and you let the error leave `change`, the whole update is discarded. The object is as it was and isn't locked.
- **A new object comes back.** `update` returns the object with its new version. The object you called it on never changes. Use the returned object for the next update: the old one is no longer the head, so updating it throws [`OBJECT_OUT_OF_DATE`](/ocfl-js/guides/errors/#object_out_of_date).
- **Only one writer at a time.** An update takes the object's lock before `change` runs. If another writer holds it, the update throws [`OBJECT_LOCKED`](/ocfl-js/guides/errors/#object_locked) straight away. See [Concurrent writers and recovery](/ocfl-js/guides/concurrent-writers/) for what to do then, and for what happens when two updates race.
- **Content is shared.** Content the object already holds, in any version, isn't stored again. Copying, renaming and reinstating store nothing new.

`root.create(id, options, build)` works the same way, except that the draft starts empty and becomes version 1.

## Draft operations

Each operation takes logical paths: the paths of files as the object presents them, such as `raw/1.wav`. Paths are normalised first, so `./raw//1.wav` is `raw/1.wav`. A path that is empty, absolute or has a `..` segment throws [`INVALID_LOGICAL_PATH`](/ocfl-js/guides/errors/#invalid_logical_path).

| Operation | What it does |
|---|---|
| `write(path, content)` | Puts one file at `path`. `content` is text (stored as UTF-8), bytes, or a stream of either, such as a Node or web stream. |
| `import(source, options?)` | Copies a file or directory from disk into the draft. |
| `copy(source, target, options?)` | Copies a file, or every file below a directory, to another path in the draft. |
| `rename(source, target, options?)` | Moves a file, or every file below a directory, to another path in the draft. |
| `reinstate(path, version)` | Puts a file, or every file below a directory, back as it was in an earlier version, at the same path. |
| `remove(path)` | Removes a file, or every file below a directory, from the draft. Earlier versions keep it. |
| `clear()` | Removes every file from the draft. |

There's no separate replace operation. Writing, importing, copying, renaming or reinstating onto a path that already has a file replaces that file. See [Replacing](#replacing).

### write

`write` stores the bytes as they were when you called it. A path that is a directory in the draft, or lies below a file, throws [`PATH_CONFLICT`](/ocfl-js/guides/errors/#path_conflict).

### import

`import` reads from your file system, not from the object.

- With the `target` option, `{ target: 'raw' }`, a file goes to that path and a directory's contents go below it.
- Without one, a file keeps its own name at the top of the object, and a directory's contents go at the top. The directory itself isn't included: importing `/data/item-1` gives `a.txt`, not `item-1/a.txt`.
- Everything below a directory is imported, including hidden files, unless the `filter` option leaves it out. See [Leaving files out](#leaving-files-out).
- Files already at the same paths are replaced. Other files in the draft stay.
- A symbolic link, or anything else that isn't a regular file or directory, that the filter doesn't leave out throws [`UNSUPPORTED_FILE_TYPE`](/ocfl-js/guides/errors/#unsupported_file_type). A file that changes while it is being read throws [`SOURCE_CHANGED`](/ocfl-js/guides/errors/#source_changed).
- If any file fails, the first failure is thrown and the draft is left as it was before the import.

#### Leaving files out

`filter` is called for each file, directory and symbolic link below the source, with its path relative to the source (using `/`, such as `sub/.DS_Store`) and its [`fs.Dirent`](https://nodejs.org/api/fs.html#class-fsdirent). Return `true` to import the entry, or `false` to leave it out; anything else, such as a promise, throws a `TypeError`. A directory left out isn't read, so everything below it is left out too, as with the `filter` option of Node's `fs.cp()`. An entry left out never fails the import, so leaving out symbolic links below the source stops them throwing `UNSUPPORTED_FILE_TYPE`.

<Code code={importFilter} lang="ts" />

The filter isn't called for the source itself: a source that is a file is imported, and one that is a symbolic link still throws `UNSUPPORTED_FILE_TYPE`.

### copy and rename

`copy` and `rename` work within the draft, so their source is a logical path, not a path on disk. A source that isn't in the draft throws [`FILE_NOT_FOUND`](/ocfl-js/guides/errors/#file_not_found). A target inside the source throws `INVALID_LOGICAL_PATH`. A source and target that are the same path do nothing.

A file copied or renamed onto an existing file replaces it. A directory copied or renamed onto a target that already has files throws [`TARGET_NOT_EMPTY`](/ocfl-js/guides/errors/#target_not_empty), unless you [merge](#merging-directories).

### reinstate

`reinstate(path, version)` takes a version number, as in `object.versions`. It puts back what was at `path` in that version and replaces whatever is there now. Other files stay. A version that doesn't exist throws [`VERSION_NOT_FOUND`](/ocfl-js/guides/errors/#version_not_found), and one that has nothing at `path` throws `FILE_NOT_FOUND`.

Reinstating from the head version undoes what the draft has done to that path so far.

### remove and clear

`remove` takes a file or a directory. A path that isn't in the draft throws `FILE_NOT_FOUND`. `clear` removes everything and never throws for an empty draft. Both change only the new version: every earlier version keeps its files. To take a file out of every version, see [Removing a file from every version](#removing-a-file-from-every-version).

### files

`files` lists what the draft holds: a map from each logical path to a [`DraftFile`](/ocfl-js/api/interfaces/draftfile/), whose `digest` is in lowercase and in the object's digest algorithm, as `OcflFile.digest` gives it. Directories aren't listed, and a new object's draft starts empty. It takes its turn like any other operation, so it shows every operation called before it, awaited or not, and none called after. The map and its files are a snapshot: later operations don't change them. It gives no content.

<Code code={draftFiles} lang="ts" />

### Catching an operation's error

An operation that is refused with an [`OcflError`](/ocfl-js/api/classes/ocflerror/), such as `FILE_NOT_FOUND`, changes nothing in the draft. If you catch the error inside `change`, the update carries on without that operation. If you don't, the update is discarded. [Errors](/ocfl-js/guides/errors/#drafts) covers each code a draft operation can throw.

## The order operations take effect in

Operations take effect in the order you call them, even when you start them together with `Promise.all`. Starting several imports together lets them read from disk at the same time, but the draft still changes in call order, whichever finishes first.

<Code code={callOrder} lang="ts" />

Here `raw/README.txt` is the text written, even if `/data/session-3/audio` holds a `README.txt` too, because the write was called after the import.

When operations touch the same path, call order decides:

- **The last one wins.** Two writes to one path leave the content of the one called second. A write after an import replaces the imported file, and an import after a write replaces the written one.
- **Each operation sees the draft as the earlier calls left it.** A `copy` or `rename` takes its source as it stands after every earlier call, and a `remove` followed by a `write` to the same path leaves the new file.
- **A copy is independent of its source.** Writing the source again after a copy leaves the copy as it was.

Await every operation you start before `change` returns. If any is still running when it returns, the update throws an `Error` and is discarded. A draft can't be used once its update has finished: every operation then throws an `Error`.

## Merging directories

Copying or renaming a directory onto a target that already has files throws `TARGET_NOT_EMPTY`. Pass `{ merge: true }` to put the directory there file by file instead: files at the same paths are replaced, and the target's other files stay.

<Code code={merge} lang="ts" />

On a single file, or onto a target with no files, `{ merge: true }` makes no difference. A file that would go where the target has a directory, or below a file, still throws `PATH_CONFLICT`.

## An update that changes nothing

If the draft ends with exactly the files of the head version, no version is written and `update` returns the same object you called it on. You can test for that with `===`.

<Code code={noChange} lang="ts" />

The draft is compared as it ends, not by what you did to it. Writing a file and removing it again, or renaming a file and back, changes nothing. Importing files that are already in the object, at the same paths with the same content, changes nothing either, which makes repeating a sync safe.

The lock and the out-of-date check still happen before `change` runs, so an update that changes nothing can still throw `OBJECT_LOCKED` or `OBJECT_OUT_OF_DATE`.

A create always writes version 1, even with no files.

## Cancelling an update

The options of `update` and `create` take an optional `signal`, an [`AbortSignal`](https://developer.mozilla.org/en-US/docs/Web/API/AbortSignal) such as a request's or `AbortSignal.timeout()`'s, next to the [version details](#version-details). The signal isn't recorded in the version.

<Code code={cancelUpdate} lang="ts" />

- A signal that is already aborted rejects with its `reason` before the lock is taken, and nothing changes.
- Once it is aborted, every draft operation called after that rejects with its `reason`, and an `import` stops between files rather than reading the rest.
- When the callback returns or throws, if the signal is aborted, the draft is discarded as for any error: nothing is committed and the lock is released. The update rejects with the signal's `reason`, even if the callback caught the error an operation rejected with.
- The signal is checked one last time just before the commit begins. After that it is ignored, and the update finishes as usual.

## Version details

The options of `update` and `create`, before the callback, hold the [version details](/ocfl-js/api/interfaces/versiondetails/) the new version records:

- `message`: why the version was made. Required, and can't be empty.
- `user`: who made it. `user.name` is required and can't be empty. `user.address` is optional: a URI for the user, such as a `mailto:` address, an ORCID, or the software's URL when [no person makes the version](#when-no-person-makes-the-version).
- `createdAt`: when the version is dated. Optional: without it, the library dates the version when it commits it, by the clock of the host doing the update. Give it to keep a version's original date, as in a migration. It can't be earlier than the head version's date; the same date, or one in the future, is allowed.

Details that break these rules throw a `TypeError` before anything else happens.

The inventory records the date as an ISO 8601 UTC timestamp. Each [version](/ocfl-js/api/interfaces/version/) gives back its `number`, `createdAt`, `message` and `user`. An object written by another tool may have versions with no message or user.
